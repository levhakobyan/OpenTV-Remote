# Compatibility research · 26 October 2026

**Current product decision (2026-10-27):** Casting has been removed from Android and iOS, including sender SDKs and temporary media servers. Casting sections below retain earlier technical research, not current product support. Native English/Russian UI, editable remotes and supported local TV transports are the current scope. The TV Companion app and its phone transports have also been removed; no separate TV receiver is supplied.


This matrix records the Android implementation. The native iPhone app has separate [iOS platform/SDK research](IOS_RESEARCH.md), [setup](../ios/README.md) and [acceptance evidence](TESTING.md#iphone-implementation-verification).

## Decision and evidence levels

Use Kotlin, Compose and provider-specific capability contracts. Prioritize Android TV because the available test hardware is Android TV. Implement Remote Service v2 from published upstream protocol sources, not an official Google third-party remote SDK. Add LG's documented legacy SSAP transport, Android Bluetooth HID and the official Google Cast sender independently. A discovered device is never evidence that all its commands work.

**D** = documented by platform/vendor; **P** = implemented or technically plausible but physical hardware verification required; **X** = unavailable, restricted, or not implemented. No physical TV was connected during development. “Documented” does not mean this app has passed vendor certification.

## Other casting options and restrictions

DIAL discovers and launches participating apps; it is not a generic media renderer or screen mirror ([DIAL specification owner](https://www.dial-multiscreen.org/)). UPnP/DLNA AVTransport can render media on some TVs but requires per-renderer SOAP capabilities, format negotiation and testing; no generic “cast to any TV” button is shipped. AirPlay and Miracast are not assumed available to an ordinary Android sender app.

Screen mirroring is **not implemented**. Android MediaProjection requires explicit consent per session, suitable foreground-service handling, encoding and a compatible receiver transport; secure content can remain black. Capture permission alone does not create a Cast mirroring sender ([Android MediaProjection](https://developer.android.com/media/grow/media-projection)).

Google's Default Media Receiver needs no custom receiver registration; styled/custom receivers require registration and separate receiver deployment ([Google receiver registration](https://developers.google.com/cast/docs/registration)). The Cast SDK is a Google Play services dependency governed by Google's terms, not a vendored open-source transport. AndroidX/Kotlin are Apache 2.0; OkHttp Apache 2.0; Bouncy Castle MIT; NanoHTTPD BSD 3-clause. Protocol research references upstream LGPL androidtvremote2 and Apache LG Connect SDK; this app implements its own bounded wire codec and transports, without bundling either SDK. Recheck distribution terms and target API requirements before a store release. Current compile/target 34 is for the available SDK/debug build and is not a claim of Play Store eligibility in 2026.

## Permissions, trust and recovery

No location, media-library, microphone, accessibility-service or Bluetooth scanning permission at startup. Wi-Fi uses INTERNET, network state and multicast lock. Bluetooth permission is contextual; file selection uses the system document picker. Future Android target upgrades must account for local-network access protections ([Android local network guidance](https://developer.android.com/privacy-and-security/local-network-permission)).

Android TV client RSA identities are AES-GCM encrypted at rest under a non-exportable Android Keystore key; successful code verification pins the TV certificate before remote control. Stored pins/LG keys use AES-GCM with a Keystore key; app backup is disabled. A reset or changed TV identity requires forgetting/re-pairing. Legacy LG traffic is plaintext, disclosed before connection, and restricted to local addresses. SSDP descriptions cannot redirect requests to another host. Local casting exposes only the selected file at a random token URL and stops in the background; use trusted Wi-Fi.

Disconnect on background, reconnect on foreground/network recovery, show failure promptly, and never replay remote actions. No automatic power commands or destructive capability probes. Physical volume response, wake, firmware permissions, text-field semantics and codec compatibility still need real-device evidence.

## UX rationale

A D-pad provides predictable, accessible navigation across input systems; touchpad gestures use D-pad commands or an available real pointer transport, with button alternatives. Back and Home sit just below it; volume and transport controls follow. Text and power appear only when negotiated. Power/settings sit in a secondary panel. App shortcuts use validated catalog or user-selected targets. Discovery is the first setup step, saved TVs support quick switching, and IP entry is a recovery path. Pairing tells users where to look and what to approve. 48dp+ targets, scrollable layouts, native semantics, system font scaling and optional haptics support comfortable use.

TLS uses a software RSA client identity to avoid opaque-key signing incompatibilities across Android TLS providers. Its PKCS12 bytes are encrypted with AES-GCM under the non-exportable Android Keystore vault key. TV certificate pinning remains mandatory after code-authenticated pairing.


## 0.2 control audit update

The user reported that Wi-Fi pairing/control worked on their TV. Model, firmware and the exact working command set were not supplied, so this is user-reported field confirmation, not a new universal hardware claim.

Android TV now exposes numeric keys, Live TV (170), input selection (178), channels (166/167), guide (172), app drawer (284), menu/info/delete, in addition to its original keys. These are ordinary Android key injections, gated by the negotiated key feature. The TV and foreground app decide how to handle them; an input/channel/TV key is not evidence of a tuner or CEC route. Source: [Android KeyEvent reference](https://developer.android.com/reference/android/view/KeyEvent).

Android TV app shortcuts use the negotiated APP_LINK feature and Remote v2 field 90; they send HTTPS links to the TV. YouTube and Netflix are editable defaults. The protocol does not expose an installed-app inventory, and a link can open in a TV browser or fail if the receiving app is absent. No successful launch is simulated. Custom shortcuts accept HTTPS only, reject embedded credentials/intent/script/file schemes, and are saved per TV. [Upstream sender](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remote.py), [schema](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remotemessage.proto), [Android link routing](https://developer.android.com/training/app-links).

LG capabilities remain unchanged. Bluetooth HID mouse mode now adds pointer/scroll after successful HID registration and connection; this reports transport availability, not observed TV-app acceptance. They do not acquire numeric, input, channel or app-launch support merely because the Android TV provider gained those commands.


Auto-keyboard uses only explicit field-22 RemoteImeShowRequest events from a paired Android TV connection. Ordinary app/counter updates do not trigger it. Valid signed protobuf offsets are parsed, and negative/no-selection statuses are ignored. The app keeps only a request ID/field counter, not the TV's existing text. Native phone Send uses the existing one-shot IME insertion; per-keystroke replacement/deletion and full Google TV-equivalent live sync are not claimed. [Published schema](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remotemessage.proto), [upstream text sender](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remote.py).

### 0.3 shortcut catalog and Live TV boundary

The ready-made catalog removes URL typing but does not add a new TV app-management API. URLs are official service entry points: [YouTube](https://www.youtube.com/), [Netflix](https://www.netflix.com/), [Prime Video](https://www.primevideo.com/), [Spotify](https://open.spotify.com/), [Disney+](https://www.disneyplus.com/), [Twitch](https://www.twitch.tv/) and [Plex](https://app.plex.tv/). Entry points were checked against official sites; no source reviewed guarantees that opening every root URL through Android TV Remote APP_LINK starts its native TV app. Treat these launch routes as requiring TV/app hardware qualification; a browser can open. [YouTube's TV guidance](https://support.google.com/youtube/answer/7640706?hl=en) and [Spotify's TV guidance](https://support.spotify.com/gd/article/spotify-on-tv/) separately require compatible TV apps and describe their own cast/connect/pairing flows; this catalog does not simulate those flows.

[Android KeyEvent documentation](https://developer.android.com/reference/android/view/KeyEvent#KEYCODE_TV) defines TV=170, TV_INPUT=178 and CHANNEL_UP=166. A Remote v2 service accepting generic key injection does not prove that the TV's firmware/current app implements a tuner action. The user reported the TV key did not open Live TV. Version 0.3 exposes an explicit user-tested TV-button mapping rather than claiming generic Live TV support. Gesture mode maps direction to existing D-pad messages; it does not claim Android TV pointer support.

### Advanced custom launch targets

Advanced users may save a publisher deep link or TV Android package ID in addition to HTTPS links. The current [androidtvremote2 client implementation](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/androidtv_remote.py) converts package IDs to `market://launch?id=…` and sends the result through APP_LINK. Luma implements that bounded format, not arbitrary intent URIs. This route needs an installed app and compatible Play Store/TV URI handler; the fixture verifies message encoding only. Native launch on the user's TV remains unverified. Deep links likewise need the app's registered handler. There is no general installed-app enumeration added to the phone app.

The built-in guide explains copying the TV app's `id=` value from its Google Play web listing (for example [Kodi](https://play.google.com/store/apps/details?id=org.xbmc.kodi), `org.xbmc.kodi`) and obtaining deep links from publisher documentation (for example [Spotify URI syntax](https://developer.spotify.com/documentation/web-api/concepts/spotify-uris-ids)). Phone/TV package variants may differ. Script/file/content/raw-intent targets are rejected; package IDs permit only bounded dot-separated identifier components. Custom launch targets are user-entered and do not bypass TV permissions or install apps.

### 0.4 motion-control decision

[Android's motion-sensor documentation](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion) defines gyroscope values as angular rates in rad/s in the phone's natural axes and requires runtime sensor availability checks. Luma samples the calibrated gyroscope at 50Hz, below Android's 200Hz high-sampling permission threshold. Gravity or an accelerometer fallback supplies posture projection for flat/upright holding. It uses relative angular movement, a dead zone and bounded output, not a camera or absolute pointing calibration. No sensor permission is requested at startup.

There are two distinct TV routes. The [LG Magic Remote guide](https://webostv.developer.lge.com/develop/guides/magic-remote) documents pointer and five-way navigation modes. The primary [ConnectSDK WebOSTV mouse socket implementation](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/master/src/com/connectsdk/service/webos/WebOSTVMouseSocketConnection.java) implements relative move messages; Luma's existing LG provider already exposes this capability only after obtaining the pointer socket. Gyroscope-driven relative cursor movement is therefore feasible for that provider, but phone/TV hardware tuning remains required. The Android TV Remote v2 provider exposes key injection, not a generic mouse-injection capability. Its alternative motion mode converts movement into directional key commands and is explicitly labeled Arrows. This does not produce a TV cursor. A general Android TV air mouse would require another compatible transport or a TV-side component; this release adds the separate Bluetooth HID mouse route below; neither route bypasses TV input-injection permissions.

Motion is opt-in through the remote menu, with a hold-to-move clutch. Sensor listeners and the ownership-bound, non-queued send pump stop on release, panel closure, lifecycle pause, capability/connection loss or TV switching. Releasing/re-holding establishes a fresh relative reference. Sensor rates, posture and perceived sensitivity still need physical-phone/TV qualification.


### 0.5 touchpad interaction

[Google's official remote guide](https://support.google.com/chromecast/answer/11221499?hl=en) describes phone swipes for navigating TV apps. The [Sony Google TV remote guide](https://www.sony.co.uk/electronics/support/televisions-projectors-oled-tvs-android-/xr-77a83l/articles/00347983) describes swiping the pad and tapping its circle to select. Luma uses the familiar swipe/select model with a larger tap-anywhere selection area, visible contact feedback and an earlier initial step. The 18dp/32dp distances and 90ms output limit are Luma implementation choices, not claims about Google's internal gesture thresholds. No new pointer capability is inferred from this UX change.

## Bluetooth mouse route (0.7)

The official [HID Device API](https://developer.android.com/reference/android/bluetooth/BluetoothHidDevice) supports combo keyboard/pointing subclass registration, `sendReport`, callbacks for registration/connection and `replyReport`. Registration depends on the phone implementation; Android unregisters apps that cease to be foreground. API support alone does not establish TV HID-host or app mouse support. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) require contextual CONNECT for bonded-device communication and ADVERTISE for discoverability on Android 12+. No scanning is used.

Luma registers keyboard report 1 and a Generic Desktop relative mouse report 2 (three button bits, padding, signed 8-bit X/Y/wheel). Touchpad taps send left-button down/up, two-finger scrolling sends wheel reports, and the gyro pointer uses the same bounded movement path. Input reports and neutral releases have unit coverage; descriptor sizes are checked. Phone registration and TV connection callbacks drive capability availability. Actual TV cursor display, wheel direction/speed, cached descriptors, screen rotation and gyro sensitivity require hardware acceptance. Keyboard-only registration provides a fallback if the TV rejects combo HID. Wi-Fi control remains a separate saved connection; there is no automatic simultaneous transport fusion or remote Internet relay.

## Samsung local integration (0.9)

The selected route is the local Tizen WebSocket channel, not SmartThings. The primary upstream source defines the `samsung.remote.control` channel, base64 client name, optional secure token, `ms.channel.connect` / unauthorized / timeout events and `ms.remote.control` key/text payloads. Samsung key availability varies by firmware/current app. Home Assistant's own integration documentation lists the compatible local ecosystem and key codes. These are protocol references, not an official universal Samsung mobile-remote SDK. The upstream Python package is LGPL-3.0 and is not bundled; Luma uses its own Kotlin state machine/codec.

Luma deliberately differs from upstream's certificate-verification bypass: an unknown leaf certificate aborts before HTTP/auth data, then a visible home-network trust action pins its SHA-256 fingerprint. Subsequent TLS requires that exact pin and selected host. This is trust on first use, not CA-verified first pairing. Certificate changes block commands and automatic downgrade; explicit pairing reset preserves layouts. Tokens and pins use the existing encrypted Vault. Unauthenticated 8001 metadata is read-only and never carries tokens. Actual plaintext control requires separate consent and displays a legacy warning; returning to secure mode retains credentials/layout.

Metadata `remote_available=false` rejects the integration; `remote_fourDirections=false` removes navigation, and `ImeSyncedSupport=true` gates manual text. The provider does not infer a real cursor from a touchpad flag. Installed-app APIs vary, Android app IDs/HTTPS shortcuts are not Samsung app IDs, and a reliable combined Play/Pause key is not established by the sources. These controls are omitted, along with off-state wake. A power key while connected does not establish wake behavior. SmartThings remains an alternative with [OAuth authorization/service integration](https://developer.smartthings.com/docs/getting-started/authorization-and-permissions), not a dependency of this implementation.

Security/session and native-flow tests use loopback TLS/WebSocket receivers. No physical Samsung model/firmware has been qualified. Normal SSDP discovery code is integrated, but emulator multicast limits do not establish physical-LAN discovery behavior.
